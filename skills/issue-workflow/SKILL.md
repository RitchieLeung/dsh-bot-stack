# 事务规则

事务（issue）是团队协作的基本单位。每件事从一个事务出发：主 Bot 接活自己派工，执行人
闭环后把结果同步回事务。你可能是主 Bot，也可能是执行人——下面两条路径都要遵守。

## 核心原则

- **主 Bot 负责调度和分发**：派给谁由主 Bot 自己按「专才 + 负载 + 能不能看图」决定，
  不是用户指定的，也不是系统替它定的。你怎么选的，就怎么跟用户说（「我按专才+负载挑了 X」，
  不要说「你指定的」）。
- **专才专业 + 负载均衡**：Bot 虽不是血肉之躯，但有用量/并发窗口限制。别把所有事务堆给同一个人，
  优先派给「能胜任且在手事务少」的同事。
- **闭环回主 Bot，不越级**：执行人做完要主动把结果同步给主 Bot；只有主 Bot 能验收（推进到「已闭环」）
  或打回重做。执行人不能自己验收自己。
- **执行人字段**：只有主 Bot（或用户）能指派/改派，执行人不能自己改执行人。

## 主 Bot 的职责（调度与分发）

1. 事务从主 Bot 出发（除非讨论里 `@` 直接点名了某位 Bot，那位就直接承接）。
2. **执行人由你自己定**（不是用户/系统指定的）：
   - 用 `list_bots` 看有哪些同事、各自现在在忙什么；
   - 用 `list_bot_models` 看谁的模型标着 "reads images"（能看图）；
   - 结合「谁在手的事少（负载）」和「专才」挑一位。
3. 用 `message_bot` 把任务交给它（reply_to 默认 me，when 现在）。message 要自包含（对方看不到你的对话）：
   事务编号、要做什么、验收标准，以及「做完用 `issue_comment` 写结果 + `issue_update` 推进到 in_review」。
   **带图片/附件时**：把附件的**本机文件路径**写进 message（对方用 `read_image` 读路径才能看到，只给 `/api/...` 链接看不到）。
4. 用 `issue_assign(事务 id, 对方名字)` 记录执行人——**这一步必须有**，否则不知道谁在办、也算不了负载。
5. 执行人交结果（in_review）后 `issue_get` 验收：合格 → `issue_update` 到 done；不合格 →
   `issue_update` 到 dispatched 并带 `rejection`（打回意见）。
6. **遇到问题要闭环**：执行人说忙/做不了/看不到图时会回来找你。你**改派**（`issue_assign` 换人）
   或**拆子事务**（`issue_create(parentId=…)`）再派。
7. **多执行人任务**（「每个 bot / 各自 / 大家」这类）：拆成每个 bot 一条子事务（`issue_create(parentId=…)`），
   逐个派、逐个验收；不要只派给一个人。

## 执行人的职责（承接与闭环）

1. 接到 `message_bot` 的事务任务后，`issue_get` 读全文和附件，自己处理。
   **图片/附件**：主 Bot 会给你附件的本机文件路径（在共享工作区里），用 `read_image` 读那个本地文件
   （不是拿 `/api/...` 链接），才能看到图。
2. 过程中有发现/结论，用 `issue_comment` 写进时间线（会同步给主 Bot）。
3. 做完了：`issue_comment` 写结果/结论，再 `issue_update` 把状态推进到 `in_review`（待验收）——
   这一步会**自动知会主 Bot 来验收**。之后等主 Bot 验收，不要自己改 done。
4. 做不了 / 正忙 / 任务太大 / 看不到图（`read_image` 报 does not declare image input）：
   **不要标待验收假装完成**。用 `issue_comment` 说明原因，再用 `message_bot` 找主 Bot 改派或拆任务。
5. 只有主 Bot 能 `done`（验收通过）或打回；你只能推进到 `in_review`。

## 评论同步

- 评论都落在事务时间线里，双方都看得到。
- 你评论 / 推进状态时，对侧（主 Bot ↔ 执行人）会自动收到知会，不用再重复 `message_bot`。

## 贴图与看图

**你有截图/产出图时，贴进评论，不要只说「已截图」却不给图。**

- 截图先落成本地文件（Playwright 就 `await page.screenshot({ path: '/tmp/shot.png' })`），
  再一次调用带上：`issue_comment(id, '说明', images: ['/tmp/shot.png'])`。
- `images` 要**绝对路径**（或 `~` 开头）：相对路径会被拒绝，因为每只 Bot 的工作目录不同。
  只认 png / jpg / jpeg / gif / webp（按文件头识别，改扩展名骗不过去），单次最多 8 张、单张 10MB。
- 只发图不写字也行；`issue_create` / `issue_update` 同样支持 `images`。

**要看别人贴的图：**

- `issue_get` 返回的 `attachments[].path` 才是本地路径，用 `read_image` 读它。
  **别拿 `attachments[].url` 去读**——那是给浏览器/人看的接口地址，Bot 读不到。
- 没有 `path` 的条目会带 `note` 说明为什么拿不到（文件被删、复制失败等），照实说，别猜图里是什么。

## 状态机（人话）

`待处理 → 讨论中 → 进行中 → 待验收 → 已闭环`，另有 `失败`、`已取消`。

- 执行人：`进行中 → 待验收`（交结果）。
- 主 Bot/用户：`待验收 → 已闭环`（验收通过）或 `待验收 → 进行中`（打回重做，必须带打回意见）。
- 打回后执行人重做，再走一遍「交结果 → 验收」。

## 注意

- 用 `message_bot` 和同事协作；不要用 dispatch_work / subagent / product_delegate 把事务
  派给自己的下属或子 agent——那些不是同事，落到它们手上事务就闭环不回来了。
- 事务工具（`issue_*`）偶尔报 unknown tool 或角色守卫拦截时，别用 dispatch_work 装样子派出去，
  在群里说明「事务工具当前不可用」并停下，等修好再领。
